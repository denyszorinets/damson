Orchestration: run.advance
==========================

``internal/controller/advance`` implements steps 1, 2, 5 and 6 of the run
lifecycle (ARCHITECTURE section 8.3) on River (ADR-0010). Dispatch, the
``step.complete`` handler, lease renewal and the reaper are separate; see
:doc:`dispatch`. Dispatch is not a River job.

Components
----------

``Advancer``
   Owns the River client (Postgres: ``riverpgxv5`` on the store's pool; SQLite:
   ``riversqlite`` on ``QueueDB``). ``Start`` and ``Stop`` follow the
   component pattern and are goleak clean. ``Enqueue(ctx, tx, runID)`` inserts
   a ``run.advance`` job on the caller's ``store.Tx``; ``Advance`` runs one
   cycle synchronously; ``Sweep`` is the safety net; ``Hub`` is the notifier.
``Hub``
   In-process change notifier. ``Subscribe(ctx, runID)`` returns a coalescing
   channel and a release function, which is the shape of ``api.RunNotifier``;
   ``cmd/damson`` passes it as ``api.Config.RunNotify``. ``Notify`` runs after
   each committed advance.

The advance cycle
-----------------

#. Load the run tree (run, step instances, executions), the job version spec
   and the job and project names.
#. Map the rows to ``engine.RunState`` with ``engine.RunStatusFromStore``,
   ``StepStatusFromStore`` and ``ExecStateFromStore`` (the store spells
   ``canceled``, the engine ``cancelled``).
#. ``engine.Decide(job, state, now)`` with an injected clock. Ids are
   generated by the store (UUIDv7), never by the engine.
#. Map the actions to one ``store.Advance`` and apply it with
   ``Tx.ApplyAdvance``: a single CAS on ``runs.version`` (+1) guards the run
   start, the new step instances and executions, queued cancellations and the
   run finish. Either all of it commits or none.
#. On a lost CAS (``ErrStale``) reload and decide again, up to five times;
   after that the job fails and River retries with backoff.
#. When ``Decide`` returns nothing to write, nothing is written and the version
   does not move, so a duplicate or late job is harmless. Specs the engine
   rejects and corrupt stored JSON cancel the job instead of retrying.

Action mapping
--------------

* ``CreateStepInstance`` plus its ``ScheduleExecution`` is one pending step
  with a queued execution. The trigger already inserts the first one with the
  run, so the first advance only emits ``start_run``
  (``TestDecideAfterTriggerInsert``).
* ``SkipStep`` and ``FailStep`` create already finished steps. ``FailStep``
  stores the ``StepError`` as JSON in ``step_instances.error``; a plain-text
  error (written elsewhere) reads back as kind ``error``. Completions store
  the agent's error the same way, as ``{"kind", "message"}``, with the kind
  ``timeout`` for ``timed_out`` and ``lost`` for an expired lease, so
  ``error.kind`` in expressions sees them; the API returns ``error`` (the
  message) and ``error_kind`` apart.
* ``CancelExecution`` cancels the execution outright only while it is
  ``queued`` (and cancels its step in the same transaction, then enqueues
  another advance because no agent report will). A dispatched or running
  execution is flagged with ``executions.cancel_requested_at``, and its owning
  controller sends ``step.cancel`` (see :doc:`dispatch`).
* The execution pool is the step's ``runs_on.pool`` from the spec, else
  ``default``; priority is 0. ``Timeout`` is stored on the execution
  (``executions.timeout_ms``, whole milliseconds, rounded up) and sent to the
  agent in ``step.execute``; the agent enforces it and reports ``timed_out``. Target resolution and labels come with the
  inventory work.

Uniqueness and wake-ups
-----------------------

The job args are ``{run_id, version}`` and the job is unique by args across
``available``, ``pending``, ``running``, ``retryable`` and ``scheduled``
(not ``completed``). River forces ``running`` into the unique states, so a job
keyed on ``run_id`` alone would drop an enqueue that arrives while an advance
runs, possibly after that advance read its state: a lost wake-up. Keying on the
version fixes it, provided every event that must wake a run changes
``runs.version`` in its own transaction:

* ``CreateRun`` (version 1), ``RequestCancel`` and ``ApplyAdvance`` bump it
  themselves.
* Anything else, for example an execution completion, calls ``Tx.TouchRun``
  first and then ``Advancer.Enqueue`` in the same transaction.

Repeated enqueues at one version collapse into one job; a change always gets a
job of its own, and the running advance either sees the change or loses its
CAS and reloads.

Safety-net sweep
----------------

At start and then every ``SweepInterval`` (default 1 minute, any controller)
``Sweep`` enqueues an advance for every ``pending`` or ``running`` run, in
batches. Uniqueness makes it cheap when a job is already waiting; a run that is
just waiting for an agent still costs one no-op job per interval and
controller (a finished job no longer blocks a new one at the same version). It
covers runs inserted before the queue existed and any crash window.
Duplicates are harmless, so correctness needs no leader lease; the leader-only
sweep of ARCHITECTURE 8.4 (M3) will remove the per-controller multiplication.

A sweep job carries a *sweep epoch* (the current time cut to the interval) in
its args, so its unique key is ``(run_id, version, epoch)``. This is what
recovers a controller crash in the middle of an advance: River leaves the dead
controller's job ``running`` and the run version does not change, so a sweep
job without the epoch would collapse into it and the run would wait for
River's rescuer. With the epoch the run moves again within one sweep interval.
Sweeps of one interval, on any controller, still collapse into each other, and
event jobs keep their old args (the field is omitted when zero). With sweeping
disabled (a negative interval) a hand-made ``Sweep`` call uses epoch 0.

River is configured with ``JobTimeout`` 1 minute (an advance is a few queries)
and ``RescueStuckJobsAfter`` 2 minutes, and jobs have ``MaxAttempts`` 5. The
rescuer only clears rows a crashed controller stranded; it is not what
recovers the run. A job discarded after five failures is replaced by the next
sweep.

Job timeout
-----------

``spec.timeout`` is decided by the engine (ADR-0035): once ``runs.started_at +
timeout`` has passed and no cancel was requested, ``Decide`` emits
``TimeoutRun`` and treats the run as cancelling in the same call. ``toAdvance``
maps it to ``Advance.CancelRun``, which the store applies inside the advance's
version CAS as ``cancel_requested_at`` with ``cancel_reason`` ``timeout``; the
executions are flagged in the same transaction and the advance enqueues itself
once more, as for any cancel.

When the run starts, ``ScheduleWake`` becomes a River job scheduled for the
deadline, inserted in the same transaction (``Args.Wake`` is the deadline in
milliseconds, version 0, so its unique key meets no other job's). A worker that
runs it before the controller's clock reaches the deadline returns
``river.JobSnooze``, which does not count as an attempt. If the wake job is
lost, the sweep times the run out within one interval.

Permanent errors
----------------

When the engine can never advance a run (a spec it rejects, corrupt stored
JSON, a change set the store refuses), the worker moves the run to ``failed``
in a version-checked transaction, logs the cause at error level, and cancels
the River job. Leaving the run ``running`` would make the sweep re-queue it
forever and a cancel would hit the same error. Runs have no error column yet,
so the cause is in the controller log only.

Store errors in an advance transaction: ``ErrStale`` means the
``runs.version`` CAS was lost and the run is reloaded (at most five times); any
other precondition failure (``ErrConflict``, for example a step that is not in
a status that can move) is not retried in a tight loop but left to River's
backoff. Cancelling a queued execution moves its step from ``pending`` or
``running``, because an execution that lost its lease goes back to ``queued``
while its step is still ``running``.

Testing
-------

``advance_test.go`` drives the cycle with a fake store and the real engine
(linear job, failure, cancel, unchanged state, version conflicts).
``integration_test.go`` runs a real River client against SQLite and, under
``-tags integration`` (``make test-pg``), Postgres: run to completion,
failure, cancel, uniqueness, rollback of the enqueue with its transaction,
eight concurrent advances applying exactly once, and the sweep.
