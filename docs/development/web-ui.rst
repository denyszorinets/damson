Web UI
======

The web UI is a SvelteKit single-page app in ``web/``: Svelte 5 (runes),
TypeScript (strict), Tailwind v4 and shadcn-svelte, built with
``adapter-static`` as an SPA (``ssr = false``). The binary embeds the build
output and serves it from every controller (:doc:`/architecture/design` §15).

Building
--------

.. code-block:: console

   $ make web          # npm ci + vite build into web/build
   $ make web-check    # prettier + eslint + svelte-check + vitest unit tests
   $ cd web && npm run dev      # Vite dev server with hot reload
   $ cd web && npm run test:unit # vitest unit tests (layout)
   $ cd web && npm run test:e2e # Playwright tests (builds the UI and runs damson dev)

``make check`` runs ``make web-check`` automatically when ``web/node_modules``
exists, so Go-only contributors do not need Node.js.

Node.js 22 or newer and npm are required. ``web/package-lock.json`` is
committed; use ``npm ci`` for reproducible installs. The Playwright tests use
the Chrome installed in the devcontainer (``/opt/google/chrome/chrome``, or
``CHROME_PATH``); do not run ``npx playwright install``.

Embedding
---------

``web/embed.go`` embeds ``web/build`` with ``go:embed all:build``, and
``internal/webui`` turns it into an ``http.Handler``:

* existing files are served as-is; files under ``_app/immutable/`` are cached
  for a year because their names are content-hashed;
* a missing ``_app/`` path or a missing path with a file extension is a 404;
* every other unknown path returns ``index.html`` (SPA fallback), so deep links
  survive a reload;
* only ``GET`` and ``HEAD`` are accepted.

``web/build`` is not committed. Only ``web/build/.gitkeep`` is, so the embed
pattern is valid on a fresh checkout and ``go build`` and ``go test`` work
without Node.js. In that case the embedded tree has no ``index.html`` and the
handler answers ``503`` with a hint to run ``make web``. Release builds must
run ``make web`` before ``go build``.

Mount the handler last, after the API and ``/healthz`` routes, so it only sees
requests they did not claim. The controller HTTP server that does this arrives
in a later M0 issue.

Components and conventions
--------------------------

* Use shadcn-svelte components from ``web/src/lib/components/ui``; add more
  with ``npx shadcn-svelte@1.7.1 add <name>`` (the CLI version used to
  generate the current components; bump it deliberately). These files are vendored and
  excluded from prettier and eslint.
* shadcn-svelte imports from ``$lib``. SvelteKit 3 deprecates the ``$lib``
  alias in favour of subpath imports, so ``vite.config.ts`` declares it
  explicitly; the build prints a deprecation notice until the upstream
  components move to subpath imports.
* ``components.json`` and the ``nova`` style were chosen by hand, because
  ``shadcn-svelte init`` is not scriptable here.
* There is no ``svelte.config.js``: the SvelteKit config is inlined in
  ``vite.config.ts``. Drop the explicit ``$lib`` alias workaround there once
  the upstream components use subpath imports.
* ``web/package.json`` sets ``engines.node`` to ``>=22``, enforced by
  ``engine-strict`` in ``web/.npmrc``.
* Call the API only through the generated client
  (``web/src/lib/api/client.ts``, types generated by ``make gen`` from
  ``web/openapi.json``; both generated files are excluded from prettier and
  eslint), and render schema-driven
  forms only through ``SchemaForm.svelte`` (CLAUDE.md, rule 10).

Pages
-----

``/agents``
   Lists agent pools (connected agents, free slots and capacity) and agents
   (status, pool, free slots and capacity, CPU, memory, one-minute load, last
   seen, labels). It reads ``GET /pools`` and ``GET /agents`` through the
   generated client, following ``next_cursor`` across pages, and refreshes
   every 5 seconds. ``lib/polling.ts`` skips ticks while the tab is hidden,
   refreshes when it becomes visible again and stops on destroy. Loading
   shows skeletons, an empty list shows a hint, and a problem+json error
   (RFC 9457) is shown in an alert while the last good data stays visible.
   Telemetry and free slots come from the agent's last heartbeat snapshot and
   show ``-`` until the first one is stored.

``/jobs``
   Lists the default project's jobs (``GET /jobs``, at most 200).

``/jobs/[id]``
   Shows the graph of the job's current version, fetched from
   ``GET /jobs/{id}/versions/{v}/graph`` (``lib/jobs.ts``). Errors
   (problem+json) are shown in an alert.

``/runs/[id]``
   The run view: the run's graph with live status, and a table of step
   instances below it (see :ref:`web-ui-run-view`).

``/secrets``
   Secret metadata and management (see :ref:`web-ui-secrets`).

``/nodes``, ``/nodes/[name]``
   The node inventory list and the node detail page (see
   :ref:`web-ui-nodes`).

Job graph view
--------------

The graph comes only from ``engine.BuildGraph`` on the server (CLAUDE.md,
rule 10, :doc:`/architecture/decisions/0020-server-built-job-graph-with-in-house-layout`).
The UI lays it out and renders it; it never reads the job spec. Files in
``web/src/lib/graph``:

``layout.ts``
   Pure function ``layout(graph)`` that places what the server sent as nested
   boxes. Lists stack top to bottom; a group wraps its body, with its ``catch``
   and ``finally`` lists as columns to the right of the body. Positions are
   relative to the parent box. The output is deterministic.
``GraphView.svelte``
   Renders the layout with ``@xyflow/svelte``. Each edge gets the class
   ``edge-<kind>`` (for example ``edge-skip``, ``edge-catch``) and is styled by it.
``GraphBox.svelte``
   The node component: label, plugin and badges for ``when``, ``retry``,
   ``for_each`` and ``continue_on_error``. It sets ``data-testid="graph-node-<id>"``
   and ``data-kind``.

Testing
~~~~~~~

``layout.test.ts`` (vitest, ``npm run test:unit``) runs the layout over every
engine golden, ``testdata/engine/graph-*.golden.json``, and checks that
children are contained in their parent, siblings do not overlap, ``catch`` and
``finally`` are right of the body, and the result is deterministic. To add or
refresh a case, change the engine fixtures and regenerate the goldens with
``go test ./internal/engine -run Graph -update``; the unit test picks the files
up without changes. ``web/e2e/jobs.test.ts`` creates a job through the API and
checks nodes by ``graph-node-<id>`` and ``data-kind``, the edge classes, that
the console has no errors, and the problem+json error path.

.. _web-ui-run-view:

Run view
--------

Data flow
~~~~~~~~~

``/runs/[id]`` fetches ``GET /runs/{id}/graph`` once (``lib/runs.ts``): the
static graph of the run's pinned version plus the current step states. It then
opens the run stream ``/api/v1/runs/{id}/events`` through ``lib/sse.ts``. Events:

``snapshot``
   Sent first on every connection; replaces the client's state.
``step``
   Upserts one step instance by its path.
``run``
   Updates the run status.
``end``
   The run is finished; the stream is closed.

SSE helper
~~~~~~~~~~

``openStream(url, options)`` in ``lib/sse.ts`` wraps ``EventSource`` and
returns a function that closes it for good. After a dropped connection the
browser reconnects itself and sends ``Last-Event-ID``; the server answers every
connection with a fresh ``snapshot``, so the handler never has to merge a gap.
If the browser gives up (the connection was refused or answered with an error
status) the helper closes the source and reopens the stream with a delay that
starts at 1 s and doubles up to 30 s; a successful open resets it. Malformed
events are ignored, and an event listed in ``endOn`` (``end``) stops the stream
without a reconnect. ``onState`` reports ``connecting``, ``live``,
``reconnecting`` and ``closed``.

Overlay
~~~~~~~

``overlay()`` in ``lib/runs.ts`` groups instances by the ``node`` and ``lane``
the server supplies. The UI never derives control flow from the spec (CLAUDE.md,
rule 10). A plain step shows its status and attempt. A ``for_each`` group and its
template nodes show lane counts by status (for example "250 lanes: 50 failed,
200 succeeded") instead of one entry per lane. ``GraphView.svelte`` takes the
result as its ``overlay`` prop and ``GraphBox.svelte`` renders it.

Bounds
~~~~~~

The DOM stays bounded however many lanes a run has: below the graph a table
lists at most 200 instances (path, lane, status, attempt, execution state) and
states how many more exist.

Testing
~~~~~~~

``runs.test.ts`` (vitest) covers the overlay, including a run with 1000 lanes.
``web/e2e/runs.test.ts`` (Playwright) covers:

* a real run on ``damson dev`` with a handled group failure: the build fails,
  the catch step is skipped, the group and the run succeed; the state survives
  a reload;
* a retried step showing attempt 2;
* a missing run, which shows the problem+json error;
* a mocked many-lanes run with the bounded list;
* a refused stream (503) that is reopened.

.. _web-ui-secrets:

Secrets page
------------

``/secrets`` lists secret metadata in a table: ref, type, field names and
version. Values are never shown. The page is not schema-driven, so it uses
plain shadcn inputs (``input``, ``label``, ``select``, ``textarea``,
``separator``) and not ``SchemaForm``. Logic lives in ``lib/secrets.ts``.

* **New secret** opens the form: scope, name and type (a select). The fields
  come from ``GET /secret-types``; the generic type lets you add named fields.
  Create sends ``if_version`` 0.
* **New version** on a row opens the same form for that ref and sends
  ``if_version`` equal to the row's current version.
* **Delete** on a row asks for an inline confirm first.
* Multiline fields use a textarea; all others use a password input. Autocomplete
  is off. Values are never pre-filled, are cleared after every submit (success
  or failure) and are not kept in the DOM after saving.

The admin token is asked for on first use and again after a 401. It is kept in
``sessionStorage`` only (gone when the tab closes) and sent as
``Authorization: Bearer`` on each call through the generated client. A
"Forget token" button removes it. The token helpers are shared with the nodes
pages (``lib/admin.ts`` and the ``TokenGate`` component).

Tests: ``lib/secrets.test.ts`` (vitest) covers field handling; the Playwright
test ``web/e2e/secrets.test.ts`` mocks the secrets API, because the dev
controller has no KEK until #115.

.. _web-ui-nodes:

Nodes pages
-----------

All ``/nodes`` routes need the admin token, reads included. Token handling is
the same as on the secrets page: the shared helpers in ``lib/admin.ts`` and the
``TokenGate`` component, ``sessionStorage`` only, a "Forget token" button and a
new prompt after a 401. Form parsing and field logic live in ``lib/nodes.ts``.
The form uses plain shadcn inputs and ``Select``, not ``SchemaForm``.

``/nodes`` lists nodes: name (a link to the detail page), ``address:port``,
transport, OS, pool, tags as badges, source, enabled or disabled, and the host
key state (pinned, observed or none) with the host key policy. The list has
source and enabled filters and a "Load more" button that follows the API
cursor, 50 nodes per page.

**New node** opens a form with name, address, port, transport (select), OS,
pool, tags (comma separated), attributes (a JSON object), credential
(``secret://`` ref), host key, host key policy (select) and enabled. It sends
``POST /nodes``. Validation problems returned by the API are shown in the form.

``/nodes/[name]`` shows all fields, the pinned and observed host key
fingerprints (SHA256), the source and the version.

* **Edit** sends ``PATCH`` with ``if_version`` set to the version the page
  read. If someone changed the node in between, the API answers 409.
* A node owned by a sync source (source other than ``manual``) can be saved or
  deleted only after ticking the explicit "Force" box. Its next sync
  overwrites the edit, and the source is kept. The box resets after each
  forced write.
* **Delete** asks for confirmation first.

Tests: ``lib/nodes.test.ts`` (vitest) covers form parsing and ``formOf`` with
null tags and attributes. The Playwright test ``web/e2e/nodes.test.ts`` mocks
the nodes API.

Dependencies and licenses
-------------------------

``@xyflow/svelte`` 1.7.1 (MIT) renders the graph; it brings ``@xyflow/system``
(MIT), ``d3-*`` (ISC) and ``@svelte-put/shortcut`` (MIT). The production tree
contains only MIT, ISC, Apache-2.0 and BSD-3-Clause. ``vitest`` (MIT) is a dev
dependency; its dev tree includes MPL-2.0, BlueOak-1.0.0 and Python-2.0, which
are never shipped (:doc:`/architecture/decisions/0033-blueoak-licensed-dev-only-tooling-dependencies`).

The secrets page adds, via shadcn-svelte, ``bits-ui`` (MIT), ``@lucide/svelte``
(ISC) and ``@internationalized/date`` (Apache-2.0).

End-to-end tests
----------------

``web/playwright.config.ts`` builds the UI, builds the ``damson`` binary into a
temporary directory and starts ``damson dev`` (controller plus one agent in one
process, SQLite in a temporary directory) on ``127.0.0.1:4174``. The tests in
``web/e2e`` run against that real API, so they need the Go toolchain.
