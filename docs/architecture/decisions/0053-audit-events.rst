ADR-0053: Audit events: table, interim actors, secret writes
============================================================

:Status: Accepted
:Date: 2026-11-06

Issue :issue:`141`. Refines ARCHITECTURE section 12.4 ("every mutation and
trigger writes an audit event"). Related: :doc:`0042-db-secret-backend-keyring`.

Context
-------

The audit log was promised but did not exist. Secret writes are the first
mutations to need it, and they arrive before OIDC, so there is no user identity
yet (the interim admin token, ARCHITECTURE section 12.2, is shared by all
admins).

Decision
--------

**Table.** ``audit_events`` (migration 00013, both dialects): ``id``, ``at``,
``actor``, ``action``, ``target_type``, ``target``, ``project_path``,
``details`` (JSON text) and ``request_id``. It is insert-only and has no
foreign keys, so an event outlives what it describes. Indexes: ``at`` and
``(target_type, target, at)``. ``project_path`` goes beyond the ARCHITECTURE
12.4 list: M8 per-subtree visibility needs it, and it cannot be backfilled
later.

**Actors.** The grammar is ``<kind>:<id>``. Until M8 the actors are
``admin-token:<first 12 hex of the stored token hash>`` (API),
``system:dev-nodes`` (the dev seeder) and ``cli:<os user>`` (``rotate-kek``;
an unauthenticated label, not proof of identity). M8 adds ``user:<sub>`` and
``sa:<id>``, and ``system:<duty>`` for controller duties.

**Actions.** ``secret.create``, ``secret.update`` (a new version),
``secret.delete``, ``secret.kek_rotate``, ``log.purge``, ``admin_token.create``
and ``admin_token.revoke`` (target type ``instance``, target ``admin_token``, empty
details: neither the token nor its hash is recorded).

**Execution target.** ``log.purge`` uses ``target_type`` ``execution`` and the
execution id as ``target``. ``LogStore.PurgeExecutionLogs`` removes all log
chunks and log objects (prefix ``logs/<execution>/``) of a terminal execution
and writes the event in the same transaction. Details: ``execution_id``,
``run_id``, ``chunks`` and ``objects``; never log content. Unknown execution:
``ErrNotFound``; not terminal: ``ErrConflict`` (HTTP 409, cancel it first);
no actor: ``ErrInvalid``. Repeating is allowed (issue :issue:`142`, see
:doc:`0047-agent-side-masking-only`).

**Details are a typed allowlist**: ``secret_id``, ``type``, ``version``, field
*names* and ``kek_id``. Never values. They are built from Go types, not from
free-form maps.

**Same transaction, fail closed.** ``CreateSecret``, ``AddSecretVersion`` and
``DeleteSecret`` write the event in the transaction of the change. An audited
write without an actor in its context fails with ``ErrInvalid``. The actor
travels in the context (``store.WithAudit``) instead of explicit parameters, a
deviation chosen for less churn across the call chain.

**Request id** is generated by the server for each admin request. An inbound
``X-Request-Id`` is not trusted.

**Read access.** ``GET /api/v1/audit`` needs the admin token; filters
``target_type`` and ``target``, cursor and ``limit`` paging, newest first.

Not audited
-----------

- Version pruning and per-row re-wraps (``rotate-kek`` writes one summary event
  per run, also when it fails).
- Failed or unauthorized attempts; the request log covers them.
- Secret reads at dispatch; they arrive with M8.
- Admin-token create and revoke are audited (``admin_token.create``,
  ``admin_token.revoke``).

Consequences
------------

- Known gap: no UI yet. Retention: :doc:`0054-audit-retention`.
- Maintainer-overridable choices: the admin-token actor label exposes a 12-hex
  prefix of the token hash; ``rotate-kek`` and admin-token create and
  revoke are audited. The event is written after the token changed (the settings
  table has no audit transaction); if writing fails the command reports that the
  token changed but the event was not recorded.
