Job orchestration that stays up.

Damson is an open-source job orchestrator in the spirit of Rundeck and a modern, minimal Jenkins. Define jobs as data, run them on stateless agents that connect out, and restart any controller at any time without losing a run. PostgreSQL is the only thing you have to operate.

  "apiVersion": "damson.dev/v1", "kind": "Job",
  "metadata": { "project": "infra/billing", "name": "uptime" },
  "spec": {
    "targets": { "selector": "'report' in node.tags" },
    "steps": [{
      "id": "per-node", "type": "group", "for_each": "targets", "max_parallel": 5,
      "steps": [{
        "id": "check", "plugin": "ssh",
        "retry": { "max_attempts": 3, "backoff": { "initial": "5s", "multiplier": 2 } },
        "with": { "node": "${{ node.name }}", "command": "uptime" }
      }]
    }]
  }
}

Built to be boring to run

Few moving parts, no consensus cluster, no broker. The database is the source of truth, and every state change is a compare-and-swap.

HA from day one

Controllers keep no durable state. Kill any controller or agent mid-run: leases expire, another controller takes over, retries follow the job's policy.

One binary, one database

A static Go binary (damson controller or damson agent) and PostgreSQL. SQLite works for development and single-controller installs.

Agents connect out

Nothing connects inbound to an agent, so pools work behind NAT, firewalls and in Kubernetes. Targets need no Damson software.

Real control flow

when conditions, try/catch/finally, retries with backoff, timeouts, cancellation and per-node fan-out.

Jobs as code

Immutable JSON job versions. damson apply and damson export sync folders with a controller; every run pins one version.

Secrets by reference

Specs hold only secret:// refs. Values are encrypted in the database or kept in OpenBao, delivered just in time and masked in logs.

OIDC and claims-based access

CEL rules over identity-provider claims grant access on a tree of projects. One expression language everywhere.

Air-gap friendly

No internet needed at runtime; the web UI is embedded. A checksummed offline bundle carries binaries, the Helm chart and systemd units.

Public plugin SDK

Built-in plugins use the same SDK as yours. Plugin forms in the UI are generated from JSON Schema.

How it works

A small controller tier talks to PostgreSQL and to agents. Agents dial in, receive steps over a WebSocket and run plugins against your nodes.

  • ssh
  • winrm
  • transfer (sftp · ftp · s3)
  • ansible
  • buildah
  • helm

Logs stream live to the UI, with ANSI rendering and resume after reconnect. Store them in the database or in S3.

Get started

Try it on one machine, then move to production with the Helm chart or systemd units.

  1. Get the binary. Download it from the latest release, or run the container image.
  2. Start a development setup. One process, SQLite, an agent included.
  3. Create a job and run it through the API or the UI at http://127.0.0.1:8080. The tutorial walks through it.
  4. Go to production. Follow the operations guide: install, upgrade, back up, run highly available, harden.
# development: controller + agent in one process
$ damson dev --dev-nodes nodes.json

# production: PostgreSQL and two controllers
$ damson migrate up
$ damson controller --config controller.toml
$ damson agent --config agent.toml

# Kubernetes
$ helm install damson ./damson-0.1.0.tgz -f values.yaml

Deployment options: Helm chart · systemd units · offline bundle.

Honest status

0.1 is the first public release. The design is complete and implemented end to end, but young software deserves caution.

ℹ️
Expect changes before 1.0. Known gaps are listed in the operations guide: OpenTelemetry traces and some metrics are not there yet, the Helm chart has not been run on a real cluster, and the offline bundle and release assets are not signed yet.
